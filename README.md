# plumb

> 铅锤。用来测一根柱子歪没歪 —— 和这个工具要回答的问题一样：**这台服务器到底哪里歪了。**

`plumb` 只回答一个问题：**这台服务器为什么慢，谁干的。**

它不画图，不存历史，不需要配置。默认运行一次，输出一份带元凶进程和证据出处的判定，然后退出；加 `-watch` 才会一直看着，而且只在情况变化时说话。

顶部三行是**状态栏**：谁、什么内核、几个核、跑了多久、负载多少、采样了多久。接下来三条 **sparkline** 是 PSI 压力的可视化——不是利用率，是「有多少时间在等」。再下面是**被堵线程表**：精确到 TID，告诉你每个线程卡在哪个内核函数（wchan）。然后才是判定和概况。

注意其中最关键的一点：同一台机器上，**`node` 是内存元凶**（4.6 GiB 常驻），**`mysqld` 是磁盘元凶**（40.1 MiB/s），而两者的 CPU 都不高。这正是利用率图表给不出的信息 —— 一张 CPU 曲线上看不出这两个人分别干了什么。

也可以自己复现这份输出，不需要 Linux 机器：

```sh
go run ./cmd/plumb -root testdata/demo/cur -prev-root testdata/demo/prev -d 1s
```

## 和监控面板的区别

| | 监控面板 / Prometheus 系 | plumb |
| --- | --- | --- |
| 回答的问题 | 现在的数字是多少 | 为什么慢，谁干的 |
| 部署 | node_exporter + Prometheus + Grafana + 告警规则 | 一个二进制，`plumb` |
| 存不存历史 | 存，需要磁盘和容量规划 | 不存，用完即走 |
| 归因 | 人来看着六张图推断 | 工具直接点名进程 |
| 告警 | 阈值规则，需要调参 | 用 PSI 测「等待」，不靠阈值拍脑袋 |
| 线程级 | 通常不采集 | 线程状态、卡在哪个内核函数、手里拿着哪些文件 |
| 依赖 | 一整套 | 只读 `/proc`，**一个子进程都不启动** |

两者不是竞品。监控面板告诉你系统在抖，`plumb` 告诉你抖动是谁造成的。

## 说人话：`-voice`

技术报告回答的是「哪里不对」，而凌晨两点的人真正想知道的是「我要不要起来」。这两件事不是一回事 —— 同一组数字，`io full avg10=17.40` 和「问题在磁盘：不是盘坏了，先别重启」落在人身上完全不同。

`-voice` 用人话复述**同一份**判定，它一个数都不重算：

```
$ plumb -voice

plumb · prod-db-01 · 严重 · 2026-09-30 16:17:09

问题在磁盘：不是盘坏了 —— 刷盘队列被塞满，写操作全在排队。
磁盘让整机停摆 —— 过去 10 秒有 24.5% 的时间所有任务都在等它
元凶 mysqld（PID 1234）：读 40.1 MiB/s，写 976.6 KiB/s。

先别重启：现场是唯一能告诉你原因的东西。用 pidstat -d 1
看是谁在写。现在就在影响线上，别等它自己好。

另有 8 项：内存、内存配额、网络、被堵住的线程、CPU 被抢占、
交换分区、单核跑满、脏页。
我只读了 /proc，没动你的系统 —— 上面每一句都能自己去核。
```

**它短是有意的。** 凌晨两点，一段长段落就是一段没人读完的段落。所以这里每一句只允许是三种东西之一：**事实、指令、边界** —— 别的都不写。第一行就是严重度，「要不要起来」不该藏在第二段里。

它由四部分拼起来，**都不依赖任何模型**：

- **严重度**（`严重` / `警告` / `注意` / `正常`）：直接放在标题行，任何散文之前。
- **性质 + 事实**：性质来自一张按判定项索引的**手写表**（磁盘 IO / 内存 / 被堵住的线程 / steal / 脏页…）；事实直接搬判定里的头条与元凶说明，**不重算**。所以「安慰的话」和「证据」不可能互相矛盾 —— 真要矛盾了，错的一定是那句安慰。
- **做什么 + 急不急**，合成一段：「先别重启」留下是因为它改变你下一步做什么，「磁盘可能存在一些问题」不留下是因为它什么都不改变。急不急按严重度校准：严重 = 现在就在影响线上；警告 = 今天之内处理掉；注意 = 先记住；信息 = 只是记录。
- **页脚**：还有什么别的，以及 plumb 没做什么。

### 有一句话被刻意禁掉了

「你的服务器貌似遇到了一点问题，不用担心，我们正在尝试介入」—— 听起来很暖。但 `plumb` 是**只读**的：不重启、不 kill、不改配置，读完 `/proc` 就退出。所以那句「我们正在尝试介入」是**撒谎**，而事故里的谎话比冷冰冰的数字更坏，因为有人会照着它做决定。

它说的是：

> 我只读了 /proc，没动你的系统 —— 上面每一句都能自己去核。

安心感只能来自**事实具体、边界清楚**，不能来自被安慰。同一个道理，它也不软化事实：平静的语气不等于乐观的结论 —— 该说「现在就在影响线上，别等它自己好」的时候就说。

## 输出模式

默认输出是**硬核终端视图**：顶部状态栏、PSI sparkline、被堵线程表、判定、概况。针对不同场景还有几种模式：

| 模式 | flag | 用途 |
| --- | --- | --- |
| 硬核（默认） | 无 | 人在终端前看：sparkline + 线程表 + 判定 |
| 纯文本 | `-raw` | 写进日志、管道、grep：无框线无颜色无块字符 |
| 求助 | `-paste` | 贴论坛/工单/群聊：ASCII + 首尾标记线，不会乱码 |
| 专家 | `-v` | 比默认多打印内核栈、打开文件、完整命令行 |
| 人话 | `-voice` | 凌晨两点看：只说性质、做什么、急不急 |
| JSON | `-json` | 给机器读：稳定结构，snake_case |

终端不支持 UTF-8 时（比如某些旧版 Windows 控制台、串口终端），plumb 会**自动降级**到 ASCII 框线和 `#=.` 块字符，不会出现乱码。也可以用 `--ascii` 强制。

## 多语言

`-lang zh|en|auto` 切换输出语言。`auto` 按 `LANG` / `LC_ALL` / `LC_MESSAGES` 检测；
`C`、`POSIX`、`C.UTF-8` 这几种都算"没选语言"，一律落到默认中文 ——
`C.UTF-8` 是 Debian/Ubuntu 没生成 locale 时的默认值，把它当成英文会在一台
从没做过选择的新机器上替用户决定。

英文模式覆盖**整份报告**：判定标题、证据、处置建议、元凶说明、概况、`-voice` 的
人话段落。有一条测试盯着这件事 —— 英文输出里出现一个汉字就失败，所以新增判定
漏翻不会悄悄溜过去。

只有**知识树的叶子正文**还是中文（89 片）。`-why` 的类别标签、可信度、用法说明
是英文的，但叶子本身写的是中文。想参与翻译的话，这是我唯一推荐从"不会 Go"
就能上手的贡献点。

## 一直看着：`-watch`

「它还在看着」这件事，一个已经退出的程序伪造不了。所以 `-watch` 是唯一的常驻模式（示意，中间整段省略）：

```
$ plumb -watch

开始盯着这台机器：每 30s 看一次，只在情况变化时说话。

plumb · prod-db-01
…
—— 情况变了：新出现 内存；变严重 磁盘 IO 警告 → 严重 ——

plumb · prod-db-01
…
```

机器没变就不出声。这不是为了省字，而是因为**每一轮都说话的监视器会被人无视，然后就不再是监视器了**。只会「记录」的信息级判定（比如一两个 D 线程 —— 那是数据库的常态瞬间）不参与差分，否则每一轮都会被算成「变了」。

`-watch` 不落盘、不写配置、不注册服务、不留任何东西。关掉终端它就没了。

## 可选的一层：`-ai`

判定层禁止接模型 —— 结论必须可复现，还要能进事故复盘。唯一允许模型介入的是**措辞与综合**：读完整份判定，说一句只有通读全篇才能说的话（比如「磁盘和内存这两条其实是同一件事的两个症状」）。

```sh
export PLUMB_AI_URL=https://你的服务/v1/chat/completions   # 给完整地址，不从 base URL 拼
export PLUMB_AI_KEY=sk-...
export PLUMB_AI_MODEL=你的模型名
plumb -ai
```

三道闸，**默认关着，坏了等于没开**：

1. **没配就报错，不静默忽略。** 打了 `-ai` 却没配 `PLUMB_AI_URL`，会明确告诉你它不生效，而不是假装用上了。
2. **12 秒不回来就放弃。** 这是在有人等着知道要不要起床时跑的，一段散文不值得让他多等。
3. **答完必过校验**：出现代码块、超过 400 字，或**任何一个两位数以上、又没出现在给它的数据里的数字** → 整段丢弃，回落成模板。一个看起来合理的伪造 PID，是这个功能能打印出来的最有害的东西 —— 那正是疲惫的运维会照着做的细节。

给模型的材料**不含命令行**：argv 里经常有密码和连接串，而诊断本来也不需要它。模型写的那段在输出里会**标注出来**（「下面这段由模型读完整份报告后写成」），和 `plumb` 自己算出来的事实分得开。

> **开 `-ai` 之前要知道**：这份诊断（主机名、进程名、判定、文件路径）会发到那台主机上。这是别人基础设施的描述，所以 plumb 每次都会把目标主机打在 stderr 上，不藏在文档里。

## 四个设计上的硬约束

### 一、绝不启动任何外部进程

`top`、`ps`、`df`、`ss`、`iostat` —— 这些都不调用。所有数据直接从 `/proc` 读。

理由不是洁癖：

1. **每调用一次 `df` 就是一次 `fork` + `exec`。** 在受监控的机器上跑监控工具，等于给已经忙不过来的机器再加负担。
2. **输出格式是别人的接口。** `ps --sort` 是 GNU 专有，Alpine 上的 busybox 没有；`ss` 在不同版本里打印的列不一样。绑上去，就绑上了对方发行版的版本。
3. **它在你最需要它的时候最慢。** 机器饱和时，调度器没有余力给你新建的子进程。采集器越忙越慢，这是监控工具里最反直觉的失败方式。

读 `/proc/stat` 是从内核内存里拷一块数据，不会阻塞在坏掉的挂载上，不受 `locale` 影响。

### 二、测「等待」，不测「利用率」

磁盘可以在 100% 利用率下愉快地处理深队列，也可以在 12% 利用率下因为一次卡住的 `fsync` 让整条请求链停下来。利用率不区分这两种情况，**PSI（Pressure Stall Information）区分** —— 它测的是「有多少时间真的有任务在等」。

- `some` = 至少一个任务在等。
- `full` = **所有**可运行任务都停住了，机器零推进。这就是「服务器卡死了」的直观感受，它的阈值远低于 `some`。

### 三、每一条判定都标出处

结论后面带着 `/proc/pressure/io`、`/proc/meminfo` 这样的来源行。你可以去核，而不是信。

不会静默归零：任何解析失败都当作错误报出来，不当作 0。对监控工具来说，把「读不到」显示成「磁盘 0%」意味着一次漏报。

### 四、绝不声称做过它没做的事

它不重启、不 kill、不改配置、不「介入」。所以它永远不说「正在为你处理」这类话 —— 事故里的谎话比冷数字更坏，因为有人会照着它做决定。它说自己做了什么，就只做了那些。`-voice` 页脚那句「没动你的系统」是这条约束的可见形式。

## 从「数字」到「结论」：线程、wchan、被堵住的文件

### 为什么 CPU 不高、磁盘读写也不大，却卡得要死

答案通常是：有线程停在 **D 状态**。

- **D = 不可中断睡眠。** 它在等 I/O，而且**连 `kill -9` 都杀不掉** —— 信号要等这次 I/O 完成才会送达。碰到杀不掉的进程别反复 kill，先看它在等什么。
- `/proc/<pid>/task/<tid>/wchan` 给出它停在内核的哪个函数上。`jbd2_log_wait_commit` 是等 ext4 日志提交，`filemap_fault` 是缺页要从磁盘读回，`io_schedule` 是等块设备完成。plumb 带一张约 50 条的内核等待点翻译表，未收录的会**原样打印函数名**，不猜。
- `/proc/<pid>/fd` 给出它手里拿着哪些文件。内核不会告诉你「是第 7 个 fd 卡住了」，但一个正在刷盘、只开着一个数据库文件的进程，答案不含糊。socket、pipe、anon_inode 与 `/dev` 会被滤掉，剩下的才是可能在磁盘上的东西。

**这类进程在吞吐量排行榜上是隐形的。** 卡在 `fsync` 上的线程几乎不传输数据，`/proc/<pid>/io` 里的读写字节能小到看不见，所以任何按 IO 量排序的排行都会把机器上最卡的进程报成「空闲」。更糟的是内核把不可中断睡眠计入 `iowait`，于是「被堵住」这件事本身还让 CPU 看起来更空闲。要看穿它，只能读线程状态和 wchan。

### wchan 只给你一个符号，栈给你整条链

wchan 是**最内层**的一个函数名。看到 `io_schedule` 你知道在等块设备，但不知道在等谁 —— 是本机的 ext4，还是一台没回应的 NFS 服务器？这两种情况的处置完全相反：前者在本机查磁盘，后者的本机重启没有任何用。

`/proc/<pid>/task/<tid>/stack` 给出完整调用栈（需要内核开 `CONFIG_STACKTRACE`，没开时 plumb 退回只报 wchan）。plumb 按栈顶前缀把它归到 10 个等待子系统，并在报告的**「内核栈判定」列**同时给出归类和**判定的那个帧**：

```
  PID     TID     COMM             WCHAN                    STATE 内核栈判定
  ──────────────────────────────────────────────────────────────────────────────
  1234    1240    mysqld           jbd2_log_wait_commit     D     ext4/jbd2 日志 ← jbd2_log_wait_commit
  1234    1241    mysqld           io_schedule              D     NFS/RPC ← nfs_wait_bit_killable
  3000    3001    node             filemap_fault            D     cgroup 内存回收 ← try_to_free_mem_cgroup_pages
```

两行的 WCHAN 看着都是「在等 I/O」，归类却完全不同：第二行根本不在本机。**箭头后面的帧是故意留的** —— 归类规则写在 `internal/probe/stack.go` 里，一个前缀顺序的改动就能改变结论，所以 plumb 把依据摊开让你自己看，而不是让你信一个结论。认不出来时这一列留空，不猜。

`plumb -v` 会把栈帧逐条打出来，加上这个进程打开的文件。

### 为什么「整机 42%」不代表没问题

CPU0 跑满、其余三个核空闲 —— 平均下来 42.5%，任何按整机平均设的阈值都不会告警。但排队排在那个满核上的请求全都在变慢。**加核心对这种结构没有任何帮助**，因为瓶颈是「一个线程干完全部活」，不是 CPU 不够；要动的是并发方式。反过来，只要这台机器还要跑别的服务，被占满的核心也会把别人一起拖慢。

## 查名字：`plumb -why`

判定里会出现 `jbd2_log_wait_commit`、`balance_dirty_pages` 这样的内核函数名。这些名字不该只有读过内核的人能看懂，也不该逼你把它复制去搜 —— 所以 plumb 内置了一棵树，`-why` 是查它的入口。

树里现在有 **89 片叶子**，分四类，键就是你在输出里已经能看到的东西：

| 类别 | 片数 | 键长什么样 |
| --- | --- | --- |
| 内核等待点 | 51 | `io_schedule`、`jbd2_log_wait_commit` —— wchan 里出现的符号 |
| 等待子系统 | 10 | `NFS/RPC`、`ext4/jbd2 日志` —— 内核栈反推出来的卡点归属 |
| 判定项 | 12 | `磁盘 IO`、`被堵住的线程` —— 报告里打印的判定名 |
| 数据来源 | 16 | `/proc/pressure/io`、`/proc/meminfo` —— 证据行里的文件 |

不给值就列出全部（同样为控制篇幅，中间用 `…` 省掉了大部分）：

```
$ plumb -why

查一片：plumb -why <键>。键可以是内核等待点符号、判定项的名字，或者 /proc
里的文件名。大小写随意，前缀能对上就行。

内核等待点（51）
  io_schedule                      线程已经进了块设备层，在等一次 IO 返回
  blk_mq_get_tag                   在等块设备队列里的一个名额（tag）
  blk_mq_freeze_queue_wait         块设备队列被冻住了，在等它放开
  …
等待子系统（10）
  ext4/jbd2 日志                   文件系统在等它自己的事务日志落盘，
                                   不是磁盘硬件慢
  NFS/RPC                          在等一个网络文件系统的服务器回应 ——
                                   这台机器本身没有问题
  …

  磁盘 IO                          这条判定看的是有多少时间在等磁盘，
                                   不是磁盘有多忙
  内存                             这条判定看的是内存压力，
                                   不是内存用了多少

                                   到顶就是 OOM kill
```

给一个键就打印那一片：

```
$ plumb -why balance_dirty_pages

balance_dirty_pages · 内核等待点 · 可信度: 有依据

它是什么
  写入者被内核按住，等脏页降到限以下。

为什么会出现
  · 这个进程写盘的速度超过了内核后台刷盘的速度，脏页堆到 vm.dirty_ratio
    附近，内核只能把写入者按停
  · 这是限流，不是盘坏了 —— 内核在拿延迟换内存不被写爆

怎么处置
  · 把 vm.dirty_background_ratio 调小，让后台刷盘更早开始：这是关键的一步
  · 不要靠调大 vm.dirty_ratio 来解决 —— 那只会让积压更深，停顿时更长
  · 用 cgroup v2 的 io.max 给这个进程限速，让它自己慢下来而不是被内核按住
  · 降低写入速率本身，或者把盘换成能跟上写入量的

看不到的地方
  这是内核主动限流，不是磁盘忙碌：iostat 上这块盘可能并不满，
  光看盘的指标找不到问题在这里。

出处
  · 内核源码 mm/page-writeback.c
  · 内核文档 Documentation/admin-guide/sysctl/
    vm.rst（dirty_background_ratio、dirty_bytes、dirty_ratio）

这一片来自内置的知识树：没有联网，也没有动你的系统。
```

大小写随意，前缀能对上就行（`shrink_` 一次给出三片），别名也认（`steal` 能查到「CPU 被抢占」）。查不到时会告诉你相近的键是哪些，而不是只回一句「没找到」—— 一个键查不到就该是**错误**（退出码 1），不能印一页看着像答案的东西。

### 三档可信度：不冒充什么都知道

这棵树最要紧的地方，是每一片都必须说清楚 **plumb 愿意为它背书到什么程度**。所以每片都带一个标签：

| 标签 | 意思 | 你能拿到什么 |
| --- | --- | --- |
| **有依据** | 原因和处置都有内核源码或官方文档支持 | 具体怎么处置 |
| **只说方向** | 原因清楚，但处置取决于 plumb 在 `/proc` 里看不到的东西（宿主机、云厂商、你的应用） | 一个大方向，外加一节「看不到的地方」 |
| **只知症状** | 有些问题根本不是机器内部能修的 | 只描述症状，并且**明说没有处置**，不编一个给你 |

第三档是有意存在的。诊断工具最坏的失败不是「不知道」，而是**不知道却编一个答案** —— 有人会照着那个答案去改生产环境。所以有些叶子就是会明说「到此为止」，那比一段听起来很有道理的建议值钱。

**出处给的是路径，不是网址。** 每一片的「出处」写的是 `mm/page-writeback.c`、`Documentation/admin-guide/sysctl/vm.rst` 这种地方 —— 网址会烂，内核源码里的文件名不会。你可以去核，而不是信。

`-why` **不采样、不读 `/proc`、不联网**：整棵树是编译进二进制的，所以在 Windows、在笔记本、在任何一台没有 `/proc` 的机器上都能用。这也是 `run` 里把它放在最前面处理的原因 —— 查一个名字，不该要求你先有一台 Linux 服务器。

## 判定项

| 判定 | 说明 |
| --- | --- |
| 磁盘 IO | PSI `io full` 高，附 IO 量最大的进程；无 PSI 时回落到 iowait |
| 内存 | PSI `memory full` 高，附常驻内存最大的进程 |
| **被堵住的线程** | 扫 `/proc/<pid>/task`，列出 D 状态线程、它卡在哪个内核函数、卡在哪个子系统、持有哪些文件 |
| CPU | PSI `cpu some` 与 busy 双判；softirq 偏高时换一套建议（网络中断而不是业务代码） |
| **CPU 被抢占** | `steal` —— 宿主机把物理 CPU 给了别的租户 |
| **单核跑满** | 逐核负载，指出被平均值掩盖的结构性瓶颈 |
| 交换分区 | 有用量即报。换入换出会让响应时间上升一个数量级，且表现为「随机变慢」 |
| 磁盘空间 | 分水位告警；虚拟设备排除在外，避免重复计算 |
| **脏页** | 脏页逼近 `vm.dirty_ratio`，内核即将同步刷盘 |
| **网络** | 重传率与 accept 队列丢弃。两者在 CPU / 内存 / 磁盘上都不留痕迹 |
| **内存配额** | 容器自己的 `memory.max`：到顶不是变慢，是 OOM kill |
| **CPU 配额** | 容器被自己的 `cpu.max` 掐停：`nr_throttled` 涨了就一定在用完配额，与宿主机忙不忙无关 |

加粗的六条是运维最难自己查的：

- **steal**：宿主机抢走的 CPU。在客户机里 `top` 看到的是一片空闲，在应用里看到的是延迟，**在客户机内调优永远无效** —— 这不是你的问题，是隔壁租户的问题。没有这个数字，运维会花几天优化一段从来不是问题所在的代码。
- **脏页**：脏页超过 `vm.dirty_ratio` 之后内核同步刷盘，此后所有 `write()` 阻塞数秒。应用表现为「随机卡顿」，日志里查不到任何东西。这个判定在它还只是**原因**、还没变成**后果**的时候抓住它。
- **被堵住的线程**：见上一节。诊断链路是「PSI 说磁盘在拖住任务」→「哪些线程在等」→「它们卡在哪个子系统、拿着哪些文件」，四段都能自己去核。
- **内核栈归类**：`wchan` 只说最内层那个函数，而它几乎总是 `io_schedule` —— 等于没说。plumb 另外读 `/proc/<pid>/task/<tid>/stack`，从整条调用链反推**是哪一层决定要等**：jbd2 日志提交、NFS 服务器、cgroup 内存回收、块设备队列，四者的处置方式彼此完全不同，判错一次就是几小时。证据行里会写出**是哪一个帧下的判断**，你可以自己核。读不到栈（内核没开 `CONFIG_STACKTRACE`，或没有 `PTRACE_MODE_READ`）时静默退回 wchan 的答案，不猜。
- **单核跑满**：整机平均是最容易骗人的一个数。
- **网络**：一台重传两成包的机器，在 CPU、内存、磁盘上全都正常 —— 只有客户端在超时。而 accept 队列丢弃的连接，应用自己根本没见过，日志里查不到。
- **内存配额**：`/proc/meminfo` 在容器里报的是宿主机的内存，所以它警告不了这件事；能警告的只有 `memory.max` 本身，而它到顶的方式是内核直接杀进程，没有「变慢」这个过渡阶段。
- **CPU 配额**：这是**唯一一种所有指标都正常、而服务确实很慢**的情形。被限流的任务不处于可运行状态，所以不计入 PSI `cpu some`、也不计入 load，CPU 使用率更是按「它得不到的时间」算的 —— 于是 CPU 那一节读起来干干净净，请求延迟却翻了三倍。而 `nr_throttled` 只有一个成因：这个 cgroup 在自己那个周期里把配额用完了。这不是推测，是计数。

## 容器里也在说实话

大多数「服务器」现在是容器。这对只读 `/proc` 的工具是个陷阱：`/proc/stat` 列出宿主机的全部核心，`/proc/meminfo` 报宿主机的内存，`/proc/pressure` 统计所有人的等待。于是 load 4.0 在 8 核宿主机上不算什么，在 2 核配额里就是排队。

plumb 读自己所在的 cgroup v2，把三件事分开：

- **限额**：`cpu.max` 换算成核数，`memory.max` 与 `memory.current` 算出配额使用率，`memory.events` 的 `max`（顶到上限几次）／`oom`（触发过几次 OOM killer）／`oom_kill`（真杀了几次）是**已经发生过几次**，不是预测。有 `memory.events.local` 时读它 —— `memory.events` 是层级汇总，会把子 cgroup 的账算到你头上。
- **限流**：`cpu.stat` 的 `nr_throttled / nr_periods`。这是被自己配额掐停的比例，有两次采样时取**窗口内的增量**（`31%` 累计但本窗口 `80%` = 此刻正在被掐；`31%` 累计但窗口 `0%` = 早就好了），只有单次采样时才给累计值并明确标注它不代表当下。
- **归属**：有 per-cgroup PSI 时，判定用它（`io.pressure` 在这一层的 full 值才是「我们在等」），并在证据里同时给出系统级读数作对照 —— 「我们卡住了」和「宿主机卡住了」是两件事。**这个 cgroup 没有自己的 PSI 时，判定只能借用 `/proc/pressure`，而那是整个节点的** —— plumb 会在证据里写明这一点，而不是把邻居的等待当成你的。
- **指认**：`单核跑满` 在配额下不会凭空点名。逐核行来自宿主机，所以这一项要求 `/proc/<pid>/stat` 的字段 39（进程最后运行在哪个核上）与那个满核对得上才报；对不上就沉默。

宿主机上没有限额时（裸机、未设限的 cgroup）这几行不会出现 —— 那是不需要说话的情形，plumb 不打印一行零。

## Kubernetes

在 Pod 里跑，plumb 会多出三样东西，全是只读一个文件得来的：

- **身份**：从 `/proc/self/cgroup` 读出 Pod UID、容器 ID、QoS 等级、容器运行时（containerd / cri-o / docker / podman），打在报告头部。它是内核写下的路径，不是猜的 —— hostname 只在没人设过 `hostname:` 时才等于 Pod 名，Downward API 要求 Pod 是为你写的。报告带身份，二十个节点捞回二十份快照才能分得清。
- **CPU 配额判定**：K8s 上最典型的死法。`CPU 配额` 那条判定会把两件容易混为一谈的事分开：**撞自己的 limit** 和 **节点上在排队**。两者的处置相反 —— 前者改 `resources.limits.cpu`（或者只留 requests、去掉 limit），后者改 limit 只是让你在更挤的地方多抢一点，反而加剧排队。判据是 `nr_throttled`，它只由「自己用完配额」这一个原因增长，所以这条结论是确凿的，不是概率。
- **作用域标注**：Pod 的 cgroup 没有自己的 PSI 时，判定借的是节点级数据。这时证据里写明「同一节点上其他 Pod 的等待也计在内 —— 有可能是邻居 Pod 在等，不是这个 Pod」。

怎么跑进去 —— 不需要插件，一条命令：

```sh
kubectl debug -it <pod> --image=<你的镜像> --target=<容器名> -- plumb -d 2s
```

ephemeral 容器与业务容器共享同一个 Pod cgroup，所以读到的是**这个 Pod 自己的**限额与限流计数。`-d 2s` 是必要的：有了两次采样才有窗口内的限流速率，也才有元凶进程。

### 为什么不做成 K8s 插件

经常有人问要不要做成 DaemonSet + 指标采集 + Grafana 面板，或者做个 Operator、CRD。不做，理由不是工作量：

- **那个位置已经站满了，而且 plumb 站在那里没有优势。** Prometheus、eBPF 那一类工具在「采集与展示」上做得比 plumb 能做到得好。plumb 的产品是**归因**：这份数据说明什么、该改什么。把它变成一组指标送进别人的面板，等于把自己唯一的部分丢掉，去补一个别人已经补上的部分。
- **「常驻」会破坏它的取证价值。** plumb 现在可以 `kubectl debug` 进去跑一次就退，不装东西、不改集群状态、不需要 RBAC。做成一个要常驻、要权限、要生命周期管理的组件之后，事故当场能不能用它，取决于它当时是不是健康的 —— 一个在故障时需要先确认自己活着的诊断工具，是没用的。
- **面板会把「判断」稀释成「数字」。** 判定之所以值钱，是因为它敢给结论、并且每一行结论都写着从哪个文件读的。摊到一张图上，读者又回到自己看六条曲线、猜哪条是原因的状态 —— 那正是 plumb 要消除的事。

所以：K8s 支持是**让 plumb 在 Pod 里说得更准**（已经做了），不是**把 plumb 变成集群里的一个服务**。JSON 输出（`-json`）给任何想消费它的系统，包含一个 `k8s` 字段和一个 `thresholds` 字段；要不要拿去画图、告警、存库，是那些系统的事。

## 权限

完整归因需要 **root**。读别人的 `/proc/<pid>/io`、`/proc/<pid>/fd`、`/proc/<pid>/wchan` 需要 `PTRACE_MODE_READ`，非 root 运行时这些文件对非自身进程读不到。

读不到时 plumb **如实报错**并把该项列入「未能测到」，不会拿 0 凑数 —— 一个读不到的计数器必须和「真的没有」区分开。以普通用户身份跑仍然能拿到整机判定（CPU、内存、PSI、磁盘、网络），缺的是元凶进程那一层。

## 用法

```

  -mount string       要检查的挂载点（默认 /）
  -top int            每个判定列出的元凶进程数上限（默认 3）

  -voice              说人话：先说这是什么性质的问题、现在该做什么，再给数字

  巡检:
  -assert             发现问题时以退出码 2 退出
  -version            打印版本

  测试 / 演示:
  -root string        用一棵假的 /proc 树代替真实根（测试 / 演示用）
  -prev-root string   前一次采样用的假树（测试 / 演示用）

  持续监控:
  -watch              一直盯着，只在情况变化时说话（隐含 -voice）
  -every duration     -watch 每隔多久看一次（默认 30s）
  -rounds int         -watch 最多看几轮后退出（默认 0 = 一直看）

  plumb config                    查看当前配置和配置文件路径

```

### 配置文件

plumb 会在 `~/.config/plumb/config.toml` 读取配置（不存在时用默认值）。flag 的优先级高于配置文件。

```toml
lang     = "auto"    # zh | en | auto
color    = "auto"    # auto | on | off
style    = "compact" # compact | raw | paste：报告的默认版式
terminal = "auto"    # auto | ascii
interval = "1s"      # 默认采样间隔
top      = 3         # 默认元凶进程数

# 判定分界线。只有下面这些行会被写进来 ——
# 没改过的项不出现在文件里，免得文件看起来比实际更权威。
[thresholds]
io_full_warn = 2.0       # 内置 2
```

键名和内置值随时可查：`plumb config` 会把十一项全列出来，改过的那几行标着
`← 已改，内置 N`。

```console
$ plumb config io_full_critical 25
已设置 io_full_critical = 25

$ plumb config
…
[thresholds]   判定分界线（括号内是 plumb 的内置值）
  io_full_warn        2
  io_full_critical    25   ← 已改，内置 10
…
```

**改过的阈值会在报告里说明。** 判定用的分界线不是内置值的时候，那条判定会多一行
`config` 证据，写清楚哪一项被改成了多少、内置是多少。一份报告要能被别人复核，
就得连"用哪条线判的"一起说 —— 两台机器、两个不同阈值的报告不能拿来直接比。

用 `plumb config` 查看和修改，不需要手动编辑文件。

### 版式：`style`

`compact`（默认，带压力条和线程表）、`raw`（纯文本，无颜色无框线，适合写日志）、
`paste`（首尾带标记线，可直接贴进工单）。`-raw` / `-paste` 这两个 flag 优先级更高：
配置文件设的是默认值，命令行决定这一次。

### 把现场存下来：快照

`plumb` 看一眼就走，但有时事故值得事后重放。`tools/snapshot` 把当前 `/proc`（可选地含
前一次采样）打成 `tar.gz`，事后任何时候解压、`plumb -root` 指过去，判定逐字复现。

```
go run ./tools/snapshot -root /proc -prev-root /tmp/proc-prev -out snap.tar.gz
tar -xzf snap.tar.gz
plumb -root snap/cur -prev-root snap/prev -d 1s
```

`snap/meta.json` 里是 hostname、plumb 版本、时间戳和命令行 —— 三个月后你重放这份快照，
能看到"当时这台机器的 plumb 会说是什么"。

格式刻意选 `tar.gz` 而不是 `zip`：服务端不装 plumb，照样能解压；体积差异在 plumb
这种几 MB 级别上不构成决策理由。

`-json` 给机器读，`-voice` / `-watch` 给人读，两者不能同时用；`-assert` 靠退出码报信、是给一次性巡检用的，和一直不退出的 `-watch` 也不能同时用；`-why` 查的是编译进二进制的树，它不采样、不出报告，所以它和上面任何一个都不能一起用 —— 这些组合会直接报错退出，而不是猜你想要哪个。

`-assert` 让它可以塞进任何脚本或 CI：

```sh
plumb -assert -json > /var/log/plumb.json || echo "机器有问题，看日志"
```

`-json` 的输出是稳定的结构，字段一律 snake_case，含义见 `internal/diagnose` 的类型定义。

## 三个退出码

| 码 | 含义 |
| --- | --- |
| 0 | 正常退出（没发现警告及以上级别的判定；`-assert` 之外始终是 0） |
| 1 | 出错了：flag 写错、找不到 `/proc`、`-ai` 没配好 |
| 2 | **发现问题**（只在 `-assert` 时） |

1 和 2 分得开是要紧的：`plumb -assert` 常被直接接进告警链路，如果 flag 写错也返回 2，一次手滑就会变成一条半夜的假告警。所以命令行错误一律走 1。

## 开发

```sh
go test ./...      # 全部测试
go vet ./...
go run ./tools/genfixture   # 重新生成演示数据集
```

演示数据集在 `testdata/demo/`，是一棵**假的 `/proc` 树**。所有采集器都通过 `probe.Root` 抽象寻址，指向这棵树就能在没有 Linux 的机器上复现完整判定：

```sh
go run ./cmd/plumb -root testdata/demo/cur -prev-root testdata/demo/prev -d 1s
```

这就是一个只支持 Linux 的工具能在一台 Windows 开发机上被测试的原因。测试里锁的都是真实踩过的坑：

- 进程可以把自己的名字取成带空格和右括号的字符串，按空白切分 `/proc/<pid>/stat` 就会解析错位。
- `/proc/<pid>/stat` 的第 42 字段（`delayacct_blkio_ticks`）在未开 `CONFIG_TASK_DELAY_ACCT` 的内核上不存在，**缺列必须标为未知而不是 0**。
- CPU 可以 offline / online 导致重新编号，逐核对比必须按 CPU ID 匹配而不是按数组位置 —— 否则会把 CPU2 的负载安到 CPU3 头上，静默产出错数字。
- 文本输出的折行也有测试：界面就是这些字。

改任何演示数据之前先跑 `go run ./tools/genfixture`，它会重建 `testdata/demo/`。

README 里的每一段示例输出都是真实捕获，不是手写的。这一点由 `tools/checkreadme.py` 保证 —— 它逐行比对 README 里的示例与对应的捕获文件（`demo.txt` / `voice.txt` / `why.txt` / `why-leaf.txt`），顺序和文字都必须一致（带 `…` 的行表示省略，跳过）：

```sh
go run ./cmd/plumb -root testdata/demo/cur -prev-root testdata/demo/prev -d 1s -no-color > demo.txt
go run ./cmd/plumb -voice -root testdata/demo/cur -prev-root testdata/demo/prev -d 1s -no-color > voice.txt
go run ./cmd/plumb -why -no-color > why.txt
go run ./cmd/plumb -why balance_dirty_pages -no-color > why-leaf.txt
python3 tools/checkreadme.py    # 重新抓过输出之后跑一次，它会指出 README 需要同步哪一行
```

捕获里的采样时间是每次运行都变的唯一内容，检查器会把日期时间归一化后再比对 —— 它不是 plumb 的行为契约，不该因为"今天是几号"就让检查失败。除此之外逐字比对，顺序和文字都必须一致（带 `…` 的行表示省略，跳过）。

## 已知局限

写在前面，省得你踩：

- **只支持 Linux。** 依赖 `/proc`。非 Linux 上只有 `-root` 指向树时才可用。
- **只认 cgroup v2。** 容器的限额与 per-cgroup PSI 都读 `/sys/fs/cgroup`（统一层级）。cgroup v1 没有 per-cgroup PSI，plumb 在那里安静地退回系统级读数，而不是报一个「限额未知」的假项。
- **只做单机。** 不聚合，不做跨机器对比，不存历史 —— `-watch` 也不落盘、不注册服务，关掉终端就什么都没有了。
- **PSI 需要内核 4.20+** 且挂载了 `CONFIG_PSI`。读不到时回落到 iowait / 内存占用率，并会在「未能测到」里如实说明。
- **「持有文件」不是「卡住的那个文件」。** 内核不报告是哪个 fd 阻塞了，只给出进程持有的文件集合。对只开着一两个数据文件的进程（数据库、日志服务）这基本就是答案；对开着几百个文件的进程，它是缩小范围用的线索。
- **线程状态是采样瞬间的快照。** 一两个 D 线程通常是正常的同步写；**数量持续偏高**才说明存储真的顶不住。所以 plumb 在证据里把这句话写出来了，而不是让你自己去想。
- **wchan 需要内核符号。** 读不到时如实报错，不假装健康。翻译表收录约 50 个常见等待点，未收录的原样打印，方便你去搜。
- **知识树不是内核文档。** 89 片叶子覆盖的是 plumb 自己会打印的符号、它读的那几个文件，以及内核栈能归类出的等待子系统，不是所有内核等待点。树里没有的符号会被原样打印，`-why` 也会直说查不到、并列出相近的键 —— 那是有意的：一棵声称无所不知的树，读者就没法判断哪一片能信。
- **知识树的叶子正文只有中文。** 报告、`-voice`、判定文本都是中英双语，但 `-why` 里的 89 片叶子还没翻译。英文模式下查到的是中文正文，类别标签和可信度是英文的。
- **阈值是可调的，但改了要自己负责。** `[thresholds]` 里十一项都能改，plumb 不会拦你；改过的项会在报告里标出来，好让别人看得出这份报告用的不是默认线。
- 归因只列「量最大的进程」和「被堵住的线程」，不做调用链追踪。它告诉你谁消耗得多、谁在等，不告诉你业务上为什么。
